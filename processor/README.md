# Сервис обработки документов (processor)

Python-сервис на FastAPI: принимает документ и шаблон полей, извлекает текст и значения полей гибридным методом «правила + NER → LLM». Вызывается веб-приложением на Laravel.

## Запуск (Windows, PowerShell)

```powershell
cd processor
python -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
copy .env.example .env   # заполнить при необходимости (ключ GigaChat и т. п.)
.venv\Scripts\python -m uvicorn app.main:app --reload --port 8001 --env-file .env
```

Порт 8001: на 8000 работает веб-приложение (`../web`). Интерактивная документация API: http://127.0.0.1:8001/docs

## Тесты

```powershell
.venv\Scripts\python -m pytest --cov
```

Тестовые документы генерируются в `tests/conftest.py`, реальные документы в репозиторий не кладутся.

## API

Все ответы в едином формате: `{"success": true, "data": {...}, "error": null}` или `{"success": false, "data": null, "error": {"code": "...", "message": "..."}}`.

### `POST /extract` (multipart/form-data)

| Поле | Тип | Описание |
|---|---|---|
| `file` | файл | PDF, DOCX, PNG или JPG (формат определяется по содержимому) |
| `template` | строка JSON | шаблон полей, см. ниже |
| `include_text` | bool | вернуть извлечённый текст (по умолчанию `false`) |
| `use_llm` | `true` / `false` | разрешить отправку фрагментов документа в LLM (по умолчанию `true`) |
| `llm_local_only` | `true` / `false` | только локальная LLM (Ollama на этом компьютере); если настроена облачная — этап пропускается с `LLM_SKIPPED_NOT_LOCAL` (по умолчанию `false`). Веб-приложение передаёт `true`, когда пользователю обещано, что документ не покидает сервер |

Шаблон:

```json
{
  "name": "Счёт на оплату",
  "fields": [
    {"name": "inn", "label": "ИНН поставщика", "data_type": "inn", "is_required": true, "keywords": ["ИНН"]},
    {"name": "total", "label": "Сумма", "data_type": "amount", "keywords": ["Итого"]}
  ]
}
```

`data_type`: `string`, `date`, `amount`, `number`, `inn`, `kpp`, `bik`, `phone`, `email`, `person`, `organization`.
Необязательные поля: `regex_pattern`, `ner_label`, `llm_hint`, `validation` (см. «Проверка значений»).

Ответ `data`: `document` (формат, страницы, страницы без текста, наличие текстового слоя, число символов), `fields` (для каждого поля — `value`, `source` = `rule` | `ner` | `llm`, `raw` — фрагмент текста для подсветки, `confidence`, `needs_review`), `llm_used`, `processing_ms`, `text`, `needs_review` и `review_fields` (см. «Проверка значений»), `warnings` — коды ситуаций, когда результат неполный, но обработка не прервана (см. раздел LLM).

### `POST /templates/validate` (multipart/form-data)

Проверка шаблона без документа — той же схемой, что в `/extract`, включая компиляцию регулярных выражений через RE2 (только сервис знает, уложится ли выражение в предел сложности). Веб-приложение вызывает её при сохранении поля с регулярным выражением. Поле формы `template` — шаблон в JSON; токен — как для `/extract`.

Ответ `data`: `{"valid": true, "issues": []}` или `{"valid": false, "issues": [{"field": "fields.1.regex_pattern", "message": "регулярное выражение слишком сложное…"}]}`. Некорректный JSON или слишком большой шаблон — ошибка `INVALID_TEMPLATE` (422).

### Проверка значений и «требует проверки»

У поля можно задать правила `validation` — нарушение не удаляет значение, а помечает поле `needs_review` с причиной в `issues`:

```json
{"name": "total", "label": "Сумма", "data_type": "amount", "keywords": ["Итого"],
 "validation": {"min_value": "1", "max_value": "10000000"}}
```

| Правило | Для типов | Причина в `issues` |
|---|---|---|
| `min_value`, `max_value` | `amount` | `OUT_OF_RANGE` |
| `min_date`, `max_date` (ГГГГ-ММ-ДД) | `date` | `OUT_OF_RANGE` |
| `max_length` | любой | `TOO_LONG` |
| `allowed_values` — список (без учёта регистра и пробелов, ё = е) | любой | `NOT_ALLOWED` |
| `pattern` — регулярное выражение RE2, значение должно совпасть целиком | любой | `INVALID_FORMAT` |

Причины, которые ставятся автоматически:

| Причина | Когда |
|---|---|
| `REQUIRED_MISSING` | обязательное поле (`is_required`) не найдено |
| `LOW_CONFIDENCE` | уверенность ниже `PROCESSOR_REVIEW_THRESHOLD` |
| `NOT_CONFIRMED` | значение от LLM не найдено в тексте документа |
| `LOW_OCR_QUALITY` | документ распознан OCR с низкой уверенностью — проверить все поля |
| `INCOMPLETE_OCR` | распознаны не все страницы (лимит страниц, таймаут, сбой) — поле могло остаться на пропущенной странице |

В ответе: у каждого поля `issues` и `needs_review = len(issues) > 0`; у документа `needs_review` и `review_fields` — список полей для проверки (веб-интерфейс показывает документ со статусом «требует проверки»).

## Как ищутся значения (этап правил)

1. Если у поля есть `regex_pattern`, используется он (через RE2; группа 1 — значение), иначе — встроенный шаблон по `data_type`.
2. Сначала поиск в «окне» после слова-якоря из `keywords` (остаток строки и следующая строка). Якорь — целое слово или фраза, без учёта регистра.
3. Если рядом с якорями ничего нет — поиск по всему документу.
4. Найденное значение нормализуется и проверяется; некорректные кандидаты отбрасываются (например, ИНН с неверной контрольной суммой, 31.02.2026).
5. Для `string` берётся остаток строки после якоря (или следующая строка); без якоря такое поле не угадывается.

| Тип | Пример в тексте | `value` |
|---|---|---|
| `date` | `12.03.2026`, `"12" марта 2026 г.` | `2026-03-12` |
| `amount` | `15 000,00 руб.` (не дата и не процент) | `15000.00` |
| `number` | `№ 15-А` | `15-А` |
| `inn` | 10 или 12 цифр с верной контрольной суммой | `7707083893` |
| `kpp` / `bik` | `773601001` / `044525225` | без изменений |
| `phone` | `+7 (912) 345-67-89`, `8-912-345-67-89` | `+79123456789` |
| `email` | `Info@Romashka.ru` | `info@romashka.ru` |
| `person` | `Иванов И.И.`, `И. И. Иванов` | `Иванов И. И.` |
| `organization` | `Общество с ограниченной ответственностью «Ромашка»`, `ИП Иванов И.И.` | `ООО "Ромашка"`, `ИП Иванов И. И.` |

Якорь — целое слово или фраза без учёта регистра; `поставщик*` — по началу слова (найдёт «поставщиком»). Окно после якоря — остаток строки; следующая строка берётся, только если строка якоря пуста и следующая не похожа на «Метка: значение» другого поля.

Уверенность (принцип: неверное значение не должно оказаться выше порога):

| Ситуация | Уверенность |
|---|---|
| одно значение рядом с якорем | 0.9 (0.95 для ИНН, телефона, e-mail) |
| значение на следующей строке после якоря | 0.8 |
| рядом с якорем несколько разных значений | 0.5 + `alternatives` |
| якоря не заданы, значение в документе одно | 0.7 (0.8 для надёжных форматов; КПП — не выше 0.5) |
| якоря заданы, но рядом с ними пусто — найдено по документу | не выше 0.5 |
| несколько разных значений по документу | 0.4 + `alternatives` |
| хвост строки для `string` | 0.65 (0.6 со следующей строки) |

## NER-этап (Natasha)

Запускается для полей `person`, `organization` и полей с явным `ner_label` (`PER`, `ORG`, `LOC`), **только если правила их не нашли или нашли с уверенностью ниже порога**. Берётся более уверенный из двух результатов (`source` = `rule` или `ner`).

- Нейросетевой NER Natasha находит людей, организации и места и приводит их к именительному падежу: «в лице директора Петрова Петра Петровича» → `Петров Петр Петрович`.
- Исправляются известные недочёты моделей: ФИО, разбитое на две сущности, склеивается; обрезанная закрывающая кавычка у организации дотягивается; аббревиатуры реквизитов (ИНН, КПП, ОГРН…) не считаются организациями.
- Запасной словарный поиск полных ФИО (`NamesExtractor`) — когда нейросеть ничего не нашла (например, ФИО отдельной строкой в шапке резюме). Он медленнее, поэтому работает только на окне после якоря или в начале документа.
- Окна и уверенность — как у правил: рядом с якорем 0.85, единственное значение в документе 0.65, несколько разных — ниже порога с `alternatives`; одно слово вместо ФИО — не выше 0.5.
- Текст подаётся в модели построчно (иначе сущности склеиваются через перевод строки); ФИО приводится к именительному падежу своей функцией с учётом рода по отчеству — «Смирнова Анна Викторовна» не превращается в «Смирнов…»; название организации берётся как в тексте.
- Бюджет NER на документ: 10 000 символов, 500 строк, 2 с; без якоря — только первые 3000 символов. Словарный поиск имён — не больше 3000 символов. В `alternatives` — не больше 3 значений (минимизация ПДн).
- `GET /health` возвращает `ner`: `ready` | `disabled` | `unavailable` и `llm`: `ready` | `disabled` | `not_configured` | `unavailable`; если включённый этап не загрузился, сервис работает дальше со статусом `degraded`.
- Модели загружаются один раз при старте сервиса (≈1 с) и только если NER включён (`PROCESSOR_NER_ENABLED`, по умолчанию `true`). Отключение этапа нужно для сравнения подходов в экспериментах.

Поля ниже `PROCESSOR_REVIEW_THRESHOLD` (по умолчанию 0.6) помечаются `needs_review` — именно они уточняются на этапе LLM. Для суммы при нескольких кандидатах предпочитается значение с копейками или валютой, затем наибольшее. `start`/`end` — позиции `raw` в извлечённом тексте (для подсветки в интерфейсе).

## OCR сканов (Tesseract)

Страницы PDF без текстового слоя и изображения PNG/JPG распознаются Tesseract (языки `rus+eng`). Страницы с текстом не распознаются повторно.

- Страница PDF рендерится в оттенки серого с `PROCESSOR_OCR_DPI` (300); разрешение снижается, если страница больше `PROCESSOR_OCR_MAX_PIXELS` (25 млн пикселей — около 100 МБ памяти Tesseract). Размеры PNG/JPG читаются из заголовка без декодирования — слишком большое изображение отклоняется (`UNSAFE_DOCUMENT`). Для JPEG разбор строгий (каждый маркер — после 0xFF) и берётся наибольший из всех объявленных кадров: подложенный маленький кадр не скрывает большой.
- Не больше `PROCESSOR_OCR_MAX_PAGES` (20) страниц и `PROCESSOR_OCR_TIMEOUT_SECONDS` (20 с) на документ; Tesseract запускается без оболочки, по абсолютному пути (поиск только по PATH, не в текущем каталоге), с таймаутом, в один поток (`OMP_THREAD_LIMIT=1`) и с минимальным окружением — ключи сервиса в процесс не передаются. Страница, которую не удалось отрендерить или распознать, пропускается; если Tesseract не запускается — остальные страницы не пробуем.
- Распознанный текст нормализуется так же, как текст PDF, и дальше обрабатывается правилами, NER и LLM.
- В `document`: `ocr_pages` — сколько страниц распознано, `ocr_confidence` — средняя уверенность Tesseract (0–100), `has_text_layer` и `pages_without_text` — состояние исходного файла (до OCR).
- Распознаются только полностью пустые страницы: скан с колонтитулом в текстовом слое (не меньше `PROCESSOR_MIN_CHARS_PER_PAGE` символов) считается текстовой страницей.

| Код в `warnings` | Когда |
|---|---|
| `OCR_PAGES_TRUNCATED` | страниц без текста больше лимита — распознаны первые |
| `OCR_PAGE_FAILED` | часть страниц не распознана (таймаут или сбой Tesseract) |
| `LOW_OCR_QUALITY` | средняя уверенность ниже `PROCESSOR_OCR_MIN_CONFIDENCE` (60) — все поля помечаются для проверки |
| `OCR_UNAVAILABLE` | в PDF есть страницы-сканы, а OCR отключён или не установлен — они пропущены |

`GET /health` → `ocr`: `ready` | `disabled` | `unavailable` (Tesseract не найден или нет русского языка — сканы не обрабатываются, статус `degraded`).

### Установка Tesseract (Windows)

1. Скачать установщик сборки UB Mannheim: https://github.com/UB-Mannheim/tesseract/wiki (файл `tesseract-ocr-w64-setup-5.x.exe`).
2. При установке в разделе **Additional language data** отметить **Russian** (английский ставится по умолчанию).
3. Указать путь в `processor/.env` (установщик не добавляет Tesseract в PATH):

```
PROCESSOR_TESSERACT_CMD=C:\Program Files\Tesseract-OCR\tesseract.exe
```

4. Проверить: `"C:\Program Files\Tesseract-OCR\tesseract.exe" --list-langs` — в списке должны быть `rus` и `eng`; после перезапуска сервиса `GET /health` → `"ocr": "ready"`.

В Docker (на шаге контейнеризации) — пакеты `tesseract-ocr` и `tesseract-ocr-rus`.

Интеграционный тест с настоящим Tesseract (`tests/test_ocr_tesseract.py`) пропускается, пока программа не установлена; остальные тесты OCR работают с подставным распознаванием.

### Общий срок обработки

`PROCESSOR_PROCESSING_BUDGET_SECONDS` (30 с — цель из паспорта проекта) делят OCR и LLM: OCR получает не больше оставшегося времени (и не больше `PROCESSOR_OCR_TIMEOUT_SECONDS`), LLM — тоже; если к этапу LLM осталось меньше `PROCESSOR_LLM_MIN_SECONDS` (5 с), запрос к модели пропускается (`warnings: LLM_SKIPPED_TIME_BUDGET`). Многостраничный скан при этом может распознаться не полностью — поля получат `INCOMPLETE_OCR`; для таких документов срок можно увеличить.

## LLM-этап (локальная модель или GigaChat)

Провайдер — `PROCESSOR_LLM_PROVIDER`: `ollama` — локальная модель на этом же компьютере (документ никуда не передаётся, рекомендуется для документов с персональными данными) или `gigachat` — облачный сервис Сбера. Остальная логика этапа у них общая.

Запускается **одним запросом на документ** для всех полей, которые правила и NER не нашли или нашли с уверенностью ниже `PROCESSOR_REVIEW_THRESHOLD`. Если все поля найдены уверенно — к LLM не обращаемся (`llm_used: false`).

- В запрос попадают описания полей (название, тип, ключевые слова, `llm_hint`), кандидаты от предыдущих этапов и текст документа. Документ до `PROCESSOR_LLM_MAX_INPUT_CHARS` (12 000) символов отправляется целиком, длиннее — начало и окна вокруг слов-якорей (`warnings: LLM_CONTEXT_TRUNCATED`).
- Модель возвращает JSON `{"поле": {"value": ..., "quote": ...}}`, где `quote` — фрагмент документа, откуда взято значение.
- Ответ модели **проверяется по тексту документа** — защита от галлюцинаций и от инструкций, спрятанных в документе:

| Ситуация | Уверенность |
|---|---|
| строгий формат (дата, сумма, ИНН, КПП, БИК, телефон, e-mail) подтверждён цитатой, рядом якорь поля | 0.8 |
| строгий формат подтверждён цитатой; или свободный текст (строка, ФИО, организация) подтверждён рядом с якорем | 0.75 |
| свободный текст подтверждён цитатой, но якоря рядом нет; или найдено само значение без цитаты | 0.55 (`needs_review`) |
| цитаты нет в тексте или она не подтверждает значение | 0.4 (`needs_review`, `raw` = null) |
| строгий формат не проходит проверки правил (контрольная сумма ИНН, 31.02) | значение отбрасывается |

Цитата ищется целыми словами, без учёта регистра и пробелов. «Подтверждает» значит: для строгих типов во фрагменте находится то же нормализованное значение; для текста каждому слову значения соответствует своё слово фрагмента с учётом падежей («Петров Петр» ↔ «Петрова Петра», «Павел» ↔ «Павлу», ё = е). Свободный текст без якоря всегда уходит на проверку: документ может «подсунуть» модели правдоподобную строку. Подсветка (`raw`, `start`, `end`) для строгих типов — само значение, для текста — найденный фрагмент.

- Значения нормализуются так же, как у правил (дата → `2026-03-05`, сумма → `15000.00`, организация → `ООО "Ромашка"`).
- Если LLM нашла то же, что правила или NER, и подтвердила это цитатой, уверенность растёт на 0.1 (неподтверждённое согласие не засчитывается: модель видит кандидатов и может их просто повторить). Если значение другое — LLM заменяет его, только когда её значение подтверждено и увереннее; второе значение уходит в `alternatives`.
- Таймаут `PROCESSOR_LLM_TIMEOUT_SECONDS` — на весь вызов (ожидание потока, получение токена, повтор, чтение ответа); ответ больше 1 МБ отбрасывается. После отказа в ключе GigaChat повторный вход — не раньше чем через 60 с.
- Запрос `/extract` с `use_llm=false` не отправляет документ в LLM (например, для документов, по которым нет согласия на передачу).
- Сбой LLM не ломает обработку: остаются результаты правил и NER, код ошибки попадает в `warnings`.

| Код в `warnings` | Когда |
|---|---|
| `LLM_UNAVAILABLE` | Ollama не запущена, нет сети, таймаут (`PROCESSOR_LLM_TIMEOUT_SECONDS`, 20 с), ошибка сервера |
| `LLM_BUSY` | занят единственный поток генерации (одна видеокарта; у физлиц GigaChat — один запрос за раз) или ответ 429 |
| `LLM_QUOTA_EXCEEDED` | закончились токены GigaChat (402) |
| `LLM_AUTH_FAILED` | неверный ключ авторизации или scope GigaChat |
| `LLM_REQUEST_REJECTED` | неверная модель или параметры (404, 422); для Ollama — модель не скачана (`ollama pull`) |
| `LLM_BAD_RESPONSE` | ответ не удалось разобрать как JSON |
| `LLM_REFUSED` | модель отказалась отвечать (`finish_reason: blacklist`) |
| `LLM_SKIPPED_NOT_LOCAL` | запрос с `llm_local_only=true`, а настроена облачная LLM (GigaChat или Ollama на другом хосте) — документ в неё не отправлен |
| `LLM_CONTEXT_TRUNCATED` | в LLM отправлена только часть длинного документа |
| `LLM_FIELDS_TRUNCATED` | полей для уточнения больше 40 — отправлены первые 40 |

### Как подключить локальную LLM (Ollama) — рекомендуется

1. Установить Ollama: https://ollama.com/download (Windows — `OllamaSetup.exe`; после установки работает в фоне).
2. Скачать модель (≈4,7 ГБ, по умолчанию в `%USERPROFILE%\.ollama\models`; другая папка — переменная `OLLAMA_MODELS` до запуска Ollama):

```
ollama pull qwen2.5:7b
```

3. В `processor/.env`: `PROCESSOR_LLM_PROVIDER=ollama` (адрес и модель по умолчанию — `http://127.0.0.1:11434`, `qwen2.5:7b`).
4. Перезапустить сервис и проверить `GET /health` → `"llm": "ready"`. При старте модель загружается в видеопамять в фоне; если Ollama не запущена, документы обрабатываются правилами и NER (`warnings: LLM_UNAVAILABLE`).

- **Модель.** Qwen 2.5 хорошо понимает русский и надёжно отвечает в JSON (запрос идёт с `format: json`, `temperature: 0`). 7B в 4-битной квантизации помещается в 8 ГБ видеопамяти; при меньшей видеокарте — `qwen2.5:3b` (`PROCESSOR_OLLAMA_MODEL`), точность ниже.
- **Окно контекста.** По умолчанию у Ollama оно 2–4 тыс. токенов, и длинный документ обрезался бы молча; сервис задаёт `PROCESSOR_OLLAMA_NUM_CTX=8192` — хватает на `LLM_MAX_INPUT_CHARS` (12 000 символов) и описание полей.
- **Скорость.** RTX 3060 Ti 8 ГБ: 2–4 с на документ, когда модель в памяти. Первая загрузка с диска — от нескольких секунд до минуты, поэтому модель подгружается при старте и держится в памяти `PROCESSOR_OLLAMA_KEEP_ALIVE` (30 мин) после последнего запроса. Без видеокарты 7B отвечает 20–60 с — увеличьте `PROCESSOR_LLM_TIMEOUT_SECONDS` и `PROCESSOR_PROCESSING_BUDGET_SECONDS` или возьмите 3B.
- **Безопасность.** По `http://` разрешены только IP-адреса этого компьютера (`127.0.0.1`, `[::1]`; имя `localhost` — нет, оно зависит от файла hosts) и имена из `PROCESSOR_OLLAMA_LOCAL_HOSTS` (в Docker Compose — соседний контейнер `ollama`): иначе документ ушёл бы по сети открытым текстом. Ollama на другом сервере — только через `https://`, и тогда документ уходит на этот сервер (`llm_local_only` такой адрес локальным не считает). Прокси из окружения и редиректы не используются. Если Ollama не запущена или модель не скачана, в журнале сервиса при старте — предупреждение «Локальная LLM не загружена».

### Как подключить GigaChat (физлицо, бесплатно)

1. Войти через Сбер ID: https://developers.sber.ru/studio/workspaces/my-space/get/gigachat-api
2. **Создать проект** → **GigaChat API**, ввести название, принять соглашение. Новым пользователям подключается тариф Freemium — бесплатные токены на 12 месяцев (Lite, Pro, Max).
3. В проекте сгенерировать **Authorization key** (Base64 от Client ID и Client Secret). Ключ показывается один раз — сразу сохранить. Scope — `GIGACHAT_API_PERS`.
4. Скачать корневой сертификат Минцифры (серверы GigaChat подписаны им, без него — `CERTIFICATE_VERIFY_FAILED`): https://www.gosuslugi.ru/crt → корневой сертификат. Сохранить как `processor/certs/russian_trusted_root_ca.pem` (формат PEM или CER в Base64).
5. Заполнить `processor/.env`:

```
PROCESSOR_LLM_PROVIDER=gigachat
PROCESSOR_GIGACHAT_AUTH_KEY=ключ_из_личного_кабинета
PROCESSOR_GIGACHAT_CA_BUNDLE=certs/russian_trusted_root_ca.pem
```

6. Перезапустить сервис (`--env-file .env`) и проверить `GET /health` → `"llm": "ready"`. Без ключа — `"llm": "not_configured"`, сервис работает на правилах и NER.

Модель по умолчанию — `GigaChat-2-Pro` (`PROCESSOR_GIGACHAT_MODEL`; также `GigaChat-2` — Lite, `GigaChat-2-Max`). Ключ хранится только в `.env` (в git не попадает) и не выводится в логи; проверка TLS-сертификатов не отключается.

**Персональные данные.** С GigaChat фрагменты документа отправляются во внешний сервис (серверы в РФ) — для реальных документов с персональными данными это нужно отразить в согласии на обработку. С локальной моделью (Ollama) документ не покидает компьютер, на котором работает сервис, и передачи третьим лицам нет. `PROCESSOR_LLM_ENABLED=false` отключает этап полностью.

### Коды ошибок

| Код | HTTP | Когда |
|---|---|---|
| `EMPTY_FILE` | 400 | пустой файл |
| `UNAUTHORIZED` | 401 | задан `PROCESSOR_API_TOKEN`, а токен не передан или неверный |
| `NOT_FOUND`, `METHOD_NOT_ALLOWED` | 404, 405 | неизвестный адрес или метод |
| `FILE_TOO_LARGE` | 413 | файл больше `PROCESSOR_MAX_FILE_MB` (проверяется до разбора запроса) |
| `UNSUPPORTED_FORMAT` | 415 | не PDF/DOCX/PNG/JPG |
| `DOCUMENT_READ_ERROR` | 422 | файл повреждён |
| `PASSWORD_PROTECTED` | 422 | PDF защищён паролем |
| `UNSAFE_DOCUMENT` | 422 | DOCX похож на zip-бомбу, слишком большие таблицы или изображение слишком большое для OCR |
| `TOO_MANY_PAGES` | 422 | страниц больше `PROCESSOR_MAX_PAGES` |
| `TEXT_TOO_LARGE` | 422 | текста больше `PROCESSOR_MAX_TEXT_CHARS` |
| `NO_TEXT_LAYER` | 422 | нет текстового слоя, а OCR отключён или не установлен; или OCR не нашёл текста |
| `OCR_FAILED` | 422 | ни одну страницу без текста не удалось распознать (таймаут или сбой Tesseract) |
| `EMPTY_DOCUMENT` | 422 | в DOCX нет текста |
| `INVALID_TEMPLATE` | 422 | некорректный шаблон |
| `VALIDATION_ERROR` | 422 | не хватает полей запроса |
| `SERVICE_BUSY` | 503 | все слоты обработки заняты дольше `PROCESSOR_QUEUE_WAIT_SECONDS` (заголовок `Retry-After`) |
| `INTERNAL_ERROR` | 500 | непредвиденная ошибка (подробности только в логе, без данных документа) |

## Безопасность

- Формат определяется по содержимому, расширение имени файла игнорируется; полиглоты (PNG/ZIP с маркером `%PDF-`) не принимаются за PDF.
- Размер тела запроса ограничивается middleware до разбора multipart (в том числе при chunked-передаче).
- DOCX проверяется на zip-бомбу (число файлов, объём после распаковки, коэффициент сжатия), таблицы разбираются по XML с лимитом строк.
- PDF: лимиты страниц и объёма текста; доступ к PyMuPDF сериализован (библиотека не потокобезопасна).
- Межсервисная аутентификация: `Authorization: Bearer <PROCESSOR_API_TOKEN>`, сравнение через `hmac.compare_digest`.
- Ответы `/extract` с `Cache-Control: no-store`; в логи пишутся только коды ошибок и тип исключения — без текста документов.
- Зависимости проверяются: `.venv\Scripts\python -m pip_audit -r requirements.txt`.

- Пользовательские `regex_pattern` выполняются через RE2 (линейное время — нет ReDoS). При проверке шаблона отклоняются: обратные ссылки, lookaround, `\C`, шаблоны с пустыми совпадениями (`\b`, `^`) и слишком «тяжёлые» (размер программы RE2 > 300 инструкций, например `(\pL?){300}x`). Не больше 20 полей с regex на шаблон; без якоря regex ищет в первых 300 тыс. символов; значения длиннее 500 символов отбрасываются (иначе `(?s).+` вернул бы весь документ в обход `include_text`).
- Поиск якорей — один проход на документ с лимитом вхождений; кандидаты кэшируются на все поля шаблона.
- Непредвиденные ошибки перехватываются до uvicorn: в лог попадают только тип исключения и кадры «файл:строка» — без текста исключения и исходных строк.
- Режим `PROCESSOR_ENV=production`: без `PROCESSOR_API_TOKEN` сервис не стартует, документация API отключена.

- Одновременных `/extract` на процесс — `PROCESSOR_MAX_CONCURRENT_EXTRACTIONS` (по умолчанию 4); BLAS работает в один поток (`OMP_NUM_THREADS=1` и др.) — для NER на мелких матрицах это в разы быстрее.
- `setuptools==80.9.0` закреплён намеренно: pymorphy2 (зависимость Natasha) импортирует `pkg_resources`, удалённый в setuptools 81. pip-audit сообщает для этой версии PYSEC-2026-3447 (исправлено в 83.0.0) — принятый риск до перехода на поддерживаемый форк pymorphy3 (отдельной задачей с регрессией тестов NER).
- LLM (Ollama): по `http://` — только адреса этого компьютера, к другому хосту — `https://`; без `user:password@`.
- LLM (GigaChat): ключ — `SecretStr` (не попадает в repr, логи и ответы), проверяется формат Base64; адреса API — только `https://` без `user:password@`; проверка TLS не отключается; прокси из окружения и редиректы не используются. Текст документа в запросе помечен как данные, маркеры блока из документа вырезаются, описания полей и кандидаты — одной строкой и с ограничением длины.

Запланировано на шаге контейнеризации: изоляция разбора PDF и Tesseract в отдельных процессах с лимитами памяти (cgroups / Job Object) и без сети, запуск от непривилегированного пользователя, internal-сеть Docker.

## Оценка качества (шаг 7)

Пакет `evaluation/`: генератор синтетической выборки, расчёт метрик и отчёт для ВКР.

```powershell
# 100 документов: по 25 счетов, актов, договоров и резюме; форматы по очереди — PDF, DOCX, скан (PDF из картинок или JPEG)
.venv\Scripts\python -m evaluation.generate --out evaluation/data/synthetic --per-type 25 --seed 2026
# режимы: rules — правила; ner — правила + NER; llm — + LLM из .env (Ollama или GigaChat; не настроена — режим пропускается)
.venv\Scripts\python -m evaluation.run --dataset evaluation/data/synthetic --modes rules,ner,llm --out evaluation/reports/synthetic
```

- **Выборка** синтетическая: вымышленные ФИО со склонением, организации, ИНН с верной контрольной суммой, разные форматы дат и сумм, синонимы меток, «отвлекающие» значения (НДС, дата договора-основания, банк, «МГУ им. М. В. Ломоносова»), необязательные поля, которых в части документов нет. Сканы — с наклоном, шумом и сжатием JPEG. Выборка детерминирована по `--seed`, в git не хранится (`evaluation/data/`).
- **Шаблоны** (`evaluation/templates.py`) — как их настроил бы пользователь: синонимы меток, типы, подсказки для LLM.
- **Метрики** — на уровне полей, микроусреднение: TP — значение верно; FN — не найдено; FP — найдено, хотя поля в документе нет; неверное значение — и FP, и FN. Сравнение без учёта регистра, пробелов, кавычек, «ё» и точки в конце.
- **Дополнительно**: доля ошибок, помеченных «требует проверки», доля лишних пометок, доля полей, принятых без участия человека; время обработки (среднее, медиана, 95-й процентиль, доля ≤ 30 с); сравнение с ручным вводом (`--manual-seconds`, по умолчанию 16 мин — оценка из модели AS-IS; `--review-seconds` — время проверки одного помеченного поля).
- **Результат**: `report.md` (таблицы для текста ВКР), `outcomes.csv` (каждое поле каждого документа), `documents.csv` (время, ошибки, предупреждения), `summary.json`.
- Тот же формат (`manifest.json` + `templates/*.json` + файлы) подходит для реальных обезличенных документов, размеченных вручную.

Текущие результаты (Tesseract 5.4, без LLM — ключ GigaChat ещё не подключён): основная выборка `evaluation/reports/synthetic/report.md` (seed 2026, по ней исправлялись правила) и контрольная `evaluation/reports/holdout/report.md` (seed 7, правила не менялись).

| Выборка | Режим | Precision | Recall | F1 | Ошибок помечено для проверки | Время, среднее / максимум |
|---|---|---|---|---|---|---|
| основная | Правила | 95,2 % | 89,6 % | 92,3 % | 68,7 % | 0,7 с / 3,6 с |
| основная | Правила + NER | 95,5 % | 96,4 % | 96,0 % | 97,0 % | 0,7 с / 3,7 с |
| контрольная | Правила | 95,1 % | 89,3 % | 92,1 % | 68,2 % | 0,7 с / 4,0 с |

Оценка помогла найти и исправить недочёты: год из даты и цифры телефона, e-mail, ИНН принимались за сумму; «Елены Михайловны» не приводилось к именительному падежу (совпадает с именительным множественного числа); «им. М. В. Ломоносова» принималось за человека. Оставшиеся ошибки — город в шапке договора (правило берёт остаток строки вместе с датой — теперь такое значение помечается для проверки; это задача LLM-этапа) и путаница OCR кириллицы и латиницы (`К-52` → `K-52`). Ограничение: обе выборки получены одним генератором (меняется только seed), документы, шаблоны и правила написаны одним автором — метрики оптимистичны. Итоговые цифры для ВКР стоит подтвердить на реальных обезличенных документах (тот же формат `manifest.json`); отчёты по ним в git не попадают (`.gitignore`). Компромисс: строка после якоря, содержащая дату, теперь всегда помечается для проверки — на реальных документах («Основание: договор от 01.01.2025») это снизит долю автоматически принятых полей.
